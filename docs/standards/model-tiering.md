# Тиринг моделей и усилий

Политика для проекта microchips-next-site (SEO/каталог-миграция, B2B аккумуляторы и ИБП, рынок Беларуси).
Перенята из проекта CRM ERP, адаптирована под single-repo структуру (frontend/ + backend/).

## Цель

Качество там, где цена ошибки высока (деньги, схема данных, публикуемые контракты,
идентичность товаров) — и экономия токенов на механической работе (сканы, чтение
источников, форматирование, скаффолд). Модель и уровень усилия выбираются под задачу,
а не берутся по умолчанию самые дорогие.

## Тиры моделей

| Тир | Цена (вход/выход, $/млн токенов) | Когда | Почему |
|---|---|---|---|
| **Haiku 4.5** | $1 / $5 | Широкие сканы репозитория, чтение источников (Bitrix-выгрузки, SQL-дампы), скаффолд файлов, форматирование, markdown-заметки | Механическая работа без суждения — дешевизна и скорость важнее качества рассуждения |
| **Sonnet 5** | $2 / $10 | Ревью кода, портирование прототипов, написание тестов, верификация с суждением (но не денежная/схемная) | Баланс качества и цены для обычной инженерной работы |
| **Opus 4.8** | $5 / $25 | Деньги (цены, наличие, реквизиты), миграции схемы БД, контракты API (lead-форма ↔ LeadController), адверсариальный судья находок, арбитраж между конфликтующими источниками | Цена ошибки высока — нужен максимально надёжный анализ |

**Fable 5 — вне тиринга.** Флагман, $10 / $50 за млн токенов (10× дороже Haiku). Не дефолт.
Звать точечно только если Opus доказанно не справляется с конкретной задачей.

## Effort (усилие)

| Уровень | Типовые связки | Когда |
|---|---|---|
| **low** | Haiku + low | Механика: сканирование файлов, чтение, извлечение без интерпретации, генерация шаблонов |
| **medium** | Sonnet + medium | Обычная задача или фича: реализация, портирование, обычные тесты |
| **high** | Sonnet + high или Opus + high | Ревью, верификация находок, денежная логика, всё что требует перепроверки перед доверием |
| **xhigh / max** | Opus + xhigh/max | Архитектурные решения, миграции схемы, роль судьи/арбитра при конфликте источников |

Effort ортогонален модели: одна и та же модель может использоваться на разных уровнях
усилия в зависимости от того, насколько задаче нужна глубина рассуждения.

## В наших Workflow

- **Широкие сканы / чтение источника / скаффолд** (например: чтение Bitrix SQL gzip,
  первичное извлечение кандидатов идентичности brand+mpn, генерация черновых CSV/manifest,
  форматирование markdown-отчётов) → **Haiku + low**.
- **Портирование прототипов, доки, тесты** (например: перенос rb-b2b-*.html прототипов,
  написание PHPUnit-тестов для LeadController, документация) → **Sonnet + medium**.
- **Адверсариальная сверка находок аудита, извлечение идентичности как судья, контракты**
  (например: проверка находок audit-rb-nomenclature.py перед тем как им доверять,
  подтверждение brand/mpn кандидатов, сверка lead-формы против контракта LeadController,
  любая денежная/наличие/юрлицо логика) → **Opus + high**.
- **Fable — не дефолт.** Сабагенты не должны наследовать Fable вслепую. Понижаем тир на
  механической работе, повышаем — на деньгах и схеме.

## Наблюдение из практики

В одной из сессий воркфлоу-сабагенты гоняли рутинную экстракцию (чтение источника,
первичный парсинг) на claude-fable-5 — это утечка тира: механическая задача не требовала
флагманской модели. Явный тиринг с дефолтами по стадии (сканы → Haiku, обычная работа →
Sonnet, деньги/схема → Opus, Fable только по явному запросу) устраняет такие утечки.
