# Контракт импорта каталога

## 1С CSV

Команда запуска:

```powershell
php artisan catalog:stage-1c "C:\imports\catalog.csv" --delimiter=";"
```

Она создаёт `import_runs` и `staged_import_records`, ловит повторяющиеся `sku`, `article`, `артикул` или `mpn` в одном файле и создаёт `duplicate_conflicts`. Команда **не создаёт и не публикует** `products` или `site_products`; это сознательный SEO- и коммерческий предохранитель.

До первого массового импорта зафиксируйте mapping исходных колонок: 1С ID, SKU, MPN, manufacturer, название, категория, напряжение, ёмкость, химия, размеры, изображения, статус. Нечитаемые или неполные значения должны оставаться `needs_review`, а не подменяться сгенерированными данными.

## Bitrix

Bitrix до cutover — read-only источник миграции. Нужны отдельные snapshots каталога, свойств, SEO-полей, URL, изображений/документов и редиректов. Импорт не имеет права менять Bitrix и не имеет права без ручного правила стереть утверждённый SEO mapping.

## Проверка и добавление в регион

После staging каждая строка получает один из статусов:

- `ready_for_review` — обязательные нормализованные поля прошли проверку: стабильный ID 1С, название и хотя бы один из SKU/MPN;
- `invalid` — строка остаётся только в staging, а причины хранятся в `validation_errors`;
- `duplicate` — найдено повторение в CSV или несовпадающий SKU/MPN уже существует в общем каталоге;
- `reviewed` — редактор явно подтвердил строку;
- `published` — строка добавлена в общий каталог и в один выбранный сайт.

В Filament доступны отдельные списки прогонов, строк и конфликтов. Открытый `duplicate_conflict` блокирует и подтверждение, и добавление в регион. Исправляйте источник или правила сопоставления, затем запускайте новый импорт; конфликт не следует закрывать формально.

Только после статуса `reviewed` редактор выбирает конкретный сайт и подтверждает действие. Система повторно валидирует исходный payload в транзакции, сохраняет автора и время review/publication, связанный товар/сайт и снимок изменённых данных. Созданный `site_product` получает `is_published=false`: это добавление в региональный каталог, но не публичная публикация. Перед открытием страницы отдельно требуются локальные коммерческие и SEO-данные.

После нормализации общий `products` не означает автоматическую публикацию. Для каждой страны редактор отдельно создаёт `site_product` с URL, видимостью, availability, ценой только при подтверждении и локальными SEO/коммерческими данными. Публично доступен только `is_published=true`.

## Exact model и MPN из внешних источников

В контуре source-backed enrichment поле `products.mpn` может хранить уникальное обозначение точной модели, присвоенное производителем, даже если каталог производителя отдельно печатает внутренний числовой «Артикул». Это допустимо только когда обозначение модели однозначно идентифицирует вариант, полностью присутствует в названии исходной карточки и подтверждено первичным источником. Нельзя автоматически считать числовой «Артикул» более надёжным: первичные каталоги также содержат опечатки и повторяющиеся значения.

Для `bitrix:*` manufacturer-primary enrichment дополнительно требует pinned staging lineage со статусом `legacy_only_draft_candidate`. Любой `hold_*` блокирует заполнение MPN, описание и preview-публикацию до отдельного решения коллизии. Новый MPN проверяется как против `mpn_normalized`, так и против `sku_normalized` всего общего каталога.

## Назначение категорий сайта (catalog:assign-site-product-categories)

Связывает уже застейдженные `site_products` с уже импортированным деревом
`site_categories` конкретного сайта. Команда **не создаёт** товары, site
products или категории — это по-прежнему зона `SiteCategoryTaxonomyImporter`
и стейджинг-конвейера выше; она только линкует существующие записи и,
опционально, проставляет химию аккумулятора (AGM/GEL).

```powershell
php artisan catalog:assign-site-product-categories microchips-by "C:\imports\assignments.csv" --apply
```

Без `--apply` (по умолчанию) — dry-run: валидация проходит, `import_runs`
получает статус `dry_run_complete`, но транзакция откатывается и в БД ничего
не меняется. `--apply` коммитит.

CSV-формат (заголовки регистронезависимы, поддержаны кириллица/варианты):

| Колонка (канон) | Синонимы заголовка | Обязательна | Значение |
| --- | --- | --- | --- |
| `product_external_id` | `productexternalid`, `товарexternalid`, `товарid`, `1сid`, `externalid` | да | внешний ID товара (совпадает с `products.external_id`) |
| `category_external_id` | `categoryexternalid`, `категорияid`, `разделid` | да | внешний ID раздела в дереве `site_categories` (`--category-source`, по умолчанию `bitrix_sections`) |
| `chemistry` | `technology`, `технология`, `химия` | нет | `AGM` или `GEL` (регистр нормализуется); пусто = колонка не заполнена |

Любой незнакомый заголовок блокирует весь прогон (не игнорируется молча).

Химия пишется в **общий** `Product::technical_attributes['chemistry']`, а не
в site-scoped слой — это физическое свойство товара, а не факт конкретного
сайта, поэтому правка из CSV одного сайта видна и другим сайтам, ссылающимся
на тот же товар. Значение помечается служебным `chemistry_provenance.source`
(`operator_supplied_csv_column`) и никогда не публикуется наружу через API —
эта колонка отфильтровывается в `SiteResolver::publicAttributes()`. Уже
подтверждённое значение (записанное стейджинг-конвейером из проверенного
источника, без этой служебной метки) никогда молча не перезаписывается: при
расхождении весь прогон блокируется (`chemistry_conflict_with_confirmed_attribute`),
при отличии только в регистре — оставляется как есть. Значение, ранее
записанное этой же командой (с её собственной меткой), свободно
перезаписывается повторным прогоном с обновлённым CSV.

`is_published` эта команда никогда не читает и не пишет.

## Обязательный отчёт

Каждый прогон обязан содержать run ID, исходный файл и время, всего/успешно/ошибок, sample ошибок, conflicts и решение по ним. Публикация разрешается только после ревью отчёта и проверки результата на staging.

## Реестр строгих исключений при повторном импорте

Повторный импорт 1С обязан получать общий реестр исключённых дублей до staging:

```powershell
php artisan catalog:stage-1c "C:\imports\catalog.csv" --delimiter=";" --exclude="docs\imports\rb-strict-duplicate-exclusion-delta.csv"
```

Параметр `--exclude` можно передать несколько раз. Манифест должен быть CSV с
колонкой `product_external_id` или `external_id`. Каждая найденная строка
сохраняется в `staged_import_records` со статусом `excluded` и понятной
причиной, но не попадает в `duplicate_conflicts`, review или создание
`site_product`. Это сохраняет аудит исходной выгрузки и предотвращает
повторное появление уже доказанного дубля.
