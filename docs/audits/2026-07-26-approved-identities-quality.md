# Аудит качества 23 подтверждённых идентичностей

Дата: 2026-07-26. Источник — рабочая БД платформы (`catalog_identity_candidates`,
контур `microchips-platform`, Docker Desktop). Ничего не изменялось: только чтение
и экспорт. Товары не публиковались.

## Что выгружено

| Пакет | Одобрено | Файл |
| --- | ---: | --- |
| `rb-initial-50` | 12 | `docs/imports/2026-07-26-approved-identities-rb-initial-50.csv` |
| `rb-backlog` | 11 | `docs/imports/2026-07-26-approved-identities-rb-backlog.csv` |
| **Итого** | **23** | |

Полное состояние очереди: 23 `approved_for_staging`, 85 `pending`,
1 `rejected` (109 кандидатов).

## Дефект 1 — экспорт молча отдаёт только один пакет

`catalog:export-approved-identities` фильтрует по `--batch`, значение по
умолчанию `rb-initial-50`. Команда, записанная в
`docs/audits/2026-07-22-identity-review-workflow-loop.md`, выгружает **12 строк
из 23** и сообщает «Exported 12 approved candidates» — без единого предупреждения
о том, что ещё 11 одобренных строк остались за фильтром.

Одобрения распределены по двум пакетам, потому что первичная очередь делилась на
50 + 59. Ревьюер работал в обоих.

**Следствие:** тот, кто выполнит документированную команду и передаст результат
дальше, потеряет 48% одобренной работы, не увидев ошибки.

**Рекомендация:** добавить режим «все пакеты» (или предупреждение, когда за
фильтром остались одобренные строки другого пакета). До исправления — выгружать
каждый пакет отдельно, как сделано выше.

## Дефект 2 — 14 из 23 SKU не являются идентификаторами производителя

`confirmed_sku` во всех 23 строках — **дословная копия поля «артикул» из
номенклатуры 1С** (сверено построчно: `confirmed_sku` = `one_c_nomenclature_items.article`).

Само поле в 1С заполнено непоследовательно.

### Группа A — настоящие артикулы производителя (9 строк)

`DT12012`, `DT1212`, `DT612`, `DT1240`, `DT1207`, `DT12032`, `СК12120` — совпадают
с моделью в названии. Плюс 2 строки, где ревьюер вместо артикула указал MPN и
производителя: `СК-1209` / Восток и `GP-12-9` / Ventura.

Эти пригодны как коммерческий идентификатор.

### Группа B — внутренние коды 1С (14 строк)

Два узнаваемых шаблона:

| Шаблон | Строк | Примеры |
| --- | ---: | --- |
| `Буква + цифры с точками` | 11 | `П1.3.52.29.`, `О3.2.52.29.`, `Р3.2.52.73.`, `П1.2.52.26.` |
| `цифры\A3` | 3 | `0001\А3`, `0002\А3`, `0008\A3` |

Признаки того, что это не артикулы производителя:

- **Кириллица в префиксе** (`П`, `О`, `Р`). Артикулы Delta, Ventura, CSB, CONTACT —
  латиница.
- **Обратный слэш** в `0001\А3` — недопустимый символ для артикула.
- **Несогласованность даже внутри группы:** в `0008\A3` буква `A` латинская,
  в `0001\А3` и `0002\А3` — кириллическая `А`. Признак ручного ввода складского кода.

**Ключевое:** для всех 14 строк настоящий артикул производителя присутствует
в том же самом названии 1С:

| Записано как SKU | Название 1С | Настоящий артикул |
| --- | --- | --- |
| `П1.3.52.29.` | Delta **DT 4035** 4В 3,5Ач | DT4035 |
| `О3.2.52.29.` | Delta **DT 12045** 12В 4,5Ач | DT12045 |
| `О1.1.52.29.` | Delta **DT12022** 12В 2,2Ач | DT12022 |
| `О2.3.52.29.` | Delta **DTM 607** 6V 7Ah | DTM607 |
| `0001\А3` | Delta **DT 6015** 6В, 1,5Ач | DT6015 |
| `0002\А3` | Delta **DT 6045** 6В 4.5Ач | DT6045 |
| `0008\A3` | Delta **HR 6-9** | HR6-9 |
| `О3.1.52.26.` | CSB **HR 1234W F2** 12V/9Ah | HR1234W F2 |
| `П1.2.52.26.` | CSB **GP 12170 B1** 12V/17Ah | GP12170 B1 |
| `П1.3.52.24.` | CONTACT **GP 12-18** 12V/18Ah | GP12-18 |
| `Р3.2.52.73.` | Ventura **GP 12-1.3** | GP12-1.3 |
| `Р3.1.52.73` | Ventura **GPL 12-26** 12V/26Ah | GPL12-26 |
| `О3.2.52.73.` | Ventura **GP 12-5** 12V/5Ah | GP12-5 |
| `П2.2.52.73.` | Ventura **GP 12-2,3** 12V/2,3Ah | GP12-2.3 |

Тот же ревьюер для части строк Delta указал именно артикул (`DT1240`, `DT1207`),
а для других — складской код. То есть это неровность заполнения 1С, перенесённая
в подтверждение, а не осознанное решение.

**Почему это блокирует staging.** `confirmed_sku` становится коммерческой
идентичностью товара и ключом проверки дублей. Внутренний складской код:
(1) ничего не значит для покупателя, ищущего «Delta DT 4035»; (2) не уникален
между производителями по своей природе; (3) закрепится в карточке как «артикул».

**Действие требует человека** — правило проекта прямо запрещает выводить
идентичность автоматически. Таблица выше готова как рабочий лист: для каждой из
14 строк artikул виден в названии 1С, ревьюеру остаётся подтвердить или отклонить.

## Дефект 3 — коллизия артикула в самой 1С

Две разные позиции 1С несут **один и тот же артикул `СК1209`**:

- `СК-1209 ВОСТОК Аккумуляторная батарея`
- `Аккумуляторная батарея Ventura GP-12-9`

Это разные товары разных производителей. Артикул «Восток» проставлен на позиции
Ventura — ошибка в источнике.

Ревьюер обошёл её верно: для обеих строк `confirmed_sku` оставлен пустым, а
идентичность подтверждена через MPN + производителя (`СК-1209`/Восток и
`GP-12-9`/Ventura). Гард уникальности сработал бы и сам, но исходная ошибка
остаётся в 1С и всплывёт при следующих партиях.

**Рекомендация:** исправить артикул позиции Ventura GP-12-9 в 1С.

## Что НЕ сделано намеренно

- Значения `confirmed_sku` не изменялись: подтверждение идентичности — решение
  человека (`docs/standards/launch-policy.md` §3.1).
- `catalog:stage-1c` не запускался: до разбора группы B staging закрепил бы
  складские коды как артикулы.
- Товары не публиковались, `is_published` не менялся.

## Следующий шаг

1. Ревьюеру пройти 14 строк группы B по таблице выше и заменить складской код на
   артикул производителя (или отклонить строку, если артикул не подтверждается).
2. Исправить артикул `СК1209` у Ventura GP-12-9 в 1С.
3. Только после этого — `catalog:stage-1c` по обоим пакетам, duplicate review,
   черновики без публикации.
